================================================================================
                    PING-UP: COMPREHENSIVE INTERVIEW Q&A CHEATSHEET
================================================================================

This document outlines potential technical interview questions and answers based on
the Ping-up codebase. It covers architecture, design decisions, data flow, real-time
communication, databases, optimizations, bottlenecks, and scaling strategies.

--------------------------------------------------------------------------------
PART 1: ARCHITECTURE & HIGH-LEVEL SYSTEM DESIGN
--------------------------------------------------------------------------------

Q1: Can you describe the overall architecture of Ping-up?
A:
- Ping-up is a full-stack social networking application.
- It utilizes a decoupled Monorepo structure containing:
  1. Client/ (Frontend): React 19, Vite, Tailwind CSS 4, Redux Toolkit, and TanStack Query.
  2. server/ (Backend): Express 5 modular monolith runtime on Node.js (ES Modules).
- Cross-Cutting Infrastructure:
  - Database: MongoDB with Mongoose ODM.
  - Caching & Rate Limiting: Redis (caching profiles, tracking online status, and rate-limiting).
  - Messaging Broker: Redis Pub/Sub (for real-time message broadcasting).
  - WebSockets/Real-time Messaging: Server-Sent Events (SSE) for instant messaging, combined with 
    Stream Video/Audio SDK for video calling.
  - Background Workers: Inngest for event-driven workflows (cleaning up deleted users, sending nodemailer emails, 
    expiring 24-hour stories).
  - Authentication: Clerk (client-side Clerk Provider, server-side Clerk Express Middleware).
  - Cloud Storage: ImageKit.io for media uploads and dynamic optimizations.

Q2: What is a "Modular Monolith", and how is the backend structured using this pattern?
A:
- A modular monolith organizes code into independent, domain-centric modules (vertical slices) 
  rather than traditional horizontal layers (all controllers together, all models together).
- Inside server/modules/:
  - user/: Handles user profile, connections (following/unfollowing/requests), and user discovery.
  - post/: Handles post creation, likes, and feed generation.
  - comment/: Handles comments and nested comment replies.
  - story/: Handles short-lived 24h stories.
  - message/: Handles user-to-user messaging (SSE, Redis Pub/Sub, and call tokens).
- Each module has its own routes (`*.routes.js`), controllers (`*.controller.js`), and database schemas/models (`models/*.model.js`).
- Benefit: High cohesive code structure. If we need to scale out a domain (e.g. migrate message to a microservice), 
  all its controllers, models, and routes are already colocated, making the migration seamless.

Q3: Why was Express 5 chosen instead of Express 4 or NestJS?
A:
- Express 5 natively supports promise-based route handlers, eliminating the need for `express-async-errors` 
  or wrapping handlers in `try-catch` utilities manually to forward rejected promises to error middleware.
- Compared to NestJS, Express is lightweight and has a faster learning curve for smaller to medium development 
  teams, avoiding the boilerplate of dependency injection container configurations and TypeScript decorator-heavy code.
- Improvement: As the app grows, NestJS could be used to enforce stricter architectural patterns and TypeScript types across team members.

Q4: What is the flow of a client request from the frontend to the backend database?
A:
1. Client actions (e.g., loading a feed or sending a connection request) invoke TanStack Query or Axios.
2. The request passes the Clerk SDK, which injects a JWT Bearer Token (`Authorization: Bearer <token>`).
3. The request hits the Node/Express server.
4. Express runs global middlewares: `cors()`, `compression()`, `clerkMiddleware()`, `heartbeatMiddleware`.
5. The request hits the specific module router (e.g. `/api/user`).
6. The router applies the `rateLimiter` (Redis-backed API defense) and `protect` (verifies `req.auth()` Clerk session).
7. The route controller handles the business logic:
   - Checks Redis cache (if applicable, e.g. for profile request).
   - If a cache miss occurs, fetches data from MongoDB.
   - Saves/updates MongoDB and sets/invalidates cached data in Redis.
   - Enqueues non-critical background jobs to Inngest (e.g., sending email notifications).
8. The server responds with JSON (compressed via gzip).

PART 2: REAL-TIME COMMUNICATION (MESSAGING & CALLING)
--------------------------------------------------------------------------------

Q5: How does real-time chat work in Ping-up without WebSockets (Socket.io)?
A:
- Ping-up uses Server-Sent Events (SSE) via the HTTP protocol, combined with a Redis Pub/Sub backend broker.
- How it works:
  1. Connection: When the frontend mounts `App.jsx`, it creates an `EventSource` connection to 
     `/api/message/sse/:userId`. The server sets headers (`Content-Type: text/event-stream`, `Connection: keep-alive`) 
     and caches the active response (`res`) object in an in-memory dictionary: `connectedClients[userId] = res`.
  2. Sending: When User A sends a message to User B, it is saved to MongoDB, and then published to a Redis 
     Pub/Sub channel (`MESSAGES`) using `pubClient.publish('MESSAGES', JSON.stringify({ to_user_id, messageWithUserData }))`.
  3. Receiving: All backend server instances subscribe to the `MESSAGES` channel. When Redis broadcasts the event, 
     the server handling User B's SSE connection intercepts the message and pushes it down the HTTP event stream 
     via `connectedClients[to_user_id].write()`.
- Why SSE instead of WebSockets?
  - SSE is simpler, runs natively over HTTP (fully compatible with HTTP/2 multiplexing), automatically handles 
    reconnections, and is unidirectional (perfect for server-to-client notifications and messaging).
- Fallback: If Redis is unavailable, the server directly writes to `connectedClients[to_user_id]` locally (single-instance fallback).

Q6: What is the "Horizontal Scaling" problem with SSE/WebSockets, and how does Redis Pub/Sub solve it?
A:
- In a production environment, behind a load balancer, multiple server instances are spun up.
- Problem: If User A is connected to Instance 1, and User B is connected to Instance 2, sending a message from User A 
  would write to Instance 1's local `connectedClients` dictionary. Instance 1 cannot see User B's connection, 
  which resides on Instance 2. User B would never receive the real-time event.
- Solution: Redis Pub/Sub acts as a cross-instance coordinator. When Instance 1 publishes the message to the Redis 
  channel, Redis broadcasts it to all other active instances (including Instance 2). Instance 2 receives the message 
  via its sub-client, finds User B in its local `connectedClients` registry, and sends it to the client.

Q7: How are Voice and Video calls implemented?
A:
- The system leverages Stream.io Video SDK.
- Process:
  1. When a user starts a call, the client requests a token from the server via `/api/message/call-token`.
  2. The server generates a JWT token using Stream Node SDK (`streamClient.generateUserToken`).
  3. The client joins the room using `@stream-io/video-react-sdk`.
  4. An invite payload (`type: "call-invite"`) is pushed to the recipient in real-time through the SSE message channel.
  5. The recipient's app receives the SSE event, dispatches an `incoming-call` window custom event, which opens a calling portal 
     (rendered on top of the layout) allowing them to accept or decline the call.
- Why is it optimized?
  - On-Demand Token Generation: Tokens are only requested when a call actually begins, preventing token leakages and CPU load.
  - Persistent Call Layout: The call is integrated into the global `CallProvider` context, allowing the user to navigate pages 
    seamlessly while active on the call.

PART 3: DATA MANAGEMENT & OPTIMIZATION
--------------------------------------------------------------------------------

Q8: What MongoDB schema indexing strategies are used in the application?
A:
- Sorting Index: Placed index on `createdAt: -1` in the `Post` schema. By default, sorting query results by `createdAt` 
  forces Mongoose to perform an in-memory sort which drops performance to $O(N \log N)$ and breaks if the result set is large. 
  With an index, the sort is retrieved in $O(1)$ directly from the index tree.
- Compound Index: Compound indexes like `{ user: 1, createdAt: -1 }` on `Post` optimize finding posts for a specific user 
  sorted by date.
- Text & Pattern Indexes: Indexes on `full_name` and `location` optimize `$or` pattern queries during user discovery.

Q9: Explain the MongoDB Aggregation Pipeline used for "Recent Messages" retrieval.
A:
- In `message.controller.js`, instead of querying all messages and doing complex nested javascript loops in Node memory, 
  an aggregation pipeline is used:
  ```javascript
  Message.aggregate([
      { $match: { $or: [{ from_user_id: userId }, { to_user_id: userId }] } },
      { $sort: { createdAt: -1 } },
      { $group: { 
          _id: { $cond: [{ $eq: ["$from_user_id", userId] }, "$to_user_id", "$from_user_id"] }, 
          lastMessage: { $first: "$$ROOT" } 
      } },
      { $replaceRoot: { newRoot: "$lastMessage" } },
      { $sort: { createdAt: -1 } }
  ])
  ```
- Steps:
  1. `$match`: Filters messages involving the logged-in user (as sender or receiver).
  2. `$sort`: Sorts by `createdAt` descending so the latest message comes first.
  3. `$group`: Groups messages by the chat partner (the conditional check returns the partner's user ID). `$first: "$$ROOT"` 
     grabs the latest message object for each unique partner.
  4. `$replaceRoot`: Promotes the nested `lastMessage` object back to the top level.
  5. `$sort`: Re-sorts the final list of conversations so the most recent chat is at the top.
- Why? It runs directly in the MongoDB engine (C++ level), returning just 1 record per conversation, saving memory and 
  reducing backend CPU utilization.

Q10: What are "Query Projections" and how do they optimize database I/O?
A:
- Query projections specify the exact fields to return from the database (e.g. `.select('_id profile_picture full_name username')`).
- Why: By default, Mongoose returns entire documents, including massive attributes like cover photos, bios, followers lists, 
  and passwords (if any). By selecting only what the UI needs, we save database memory, reduce serialization overhead, 
  and minimize network payload sizes.

PART 4: CACHING & RATE LIMITING
--------------------------------------------------------------------------------

Q11: How is Redis Caching implemented for User Profiles?
A:
- Fetching: In `getUserProfile`, the controller checks if Redis contains the key `profile:${profileId}`.
  - If Cache Hit: The profile is retrieved, parsed, checked for presence (`presence:${profileId}`), and returned instantly, 
    bypassing the Mongoose database completely.
  - If Cache Miss: The profile and associated posts are fetched from MongoDB, cached in Redis with a 15-minute expiration 
    (`setEx` key for 900 seconds), and then returned.
- Cache Invalidation: To prevent stale data, when a user updates their profile details or accepts a connection request, 
  `clearUserProfileCache(userId)` is triggered to delete `profile:${profileId}` and `user:${profileId}` keys, forcing the next 
  read to fetch fresh database state.

Q12: How does Redis-backed rate limiting prevent API abuse?
A:
- A custom middleware (`rateLimiter.js`) intercepts write and sensitive endpoints.
- It increments a counter in Redis for the user's IP or user ID with a window-based time-to-live (TTL).
- If the count exceeds the threshold (e.g., 60 requests/minute), the middleware blocks the request and returns a 
  `429 Too Many Requests` status, protecting the server from brute force attacks and denial-of-service attempts.

PART 5: ASYNCHRONOUS WORKFLOWS & BACKGROUND JOBS
--------------------------------------------------------------------------------

Q13: What is Inngest, and why is it used for background jobs instead of BullMQ or cron jobs?
A:
- Inngest is an event-driven background utility that uses HTTP state delivery (serverless-compatible) to run tasks asynchronously.
- Why Inngest:
  - It does not require a persistent worker daemon process (unlike BullMQ which requires a dedicated background polling worker).
  - It provides built-in retries, event-driven triggers, and step-based execution (including stateful sleeps like waiting 24 hours).
  - It works perfectly on serverless platforms (like Vercel) and traditional VMs alike.
- Use Cases in Ping-up:
  1. `sync-user-from-clerk` / `update-user-from-clerk` / `delete-user-with-clerk`: Listens to Clerk webhooks to automatically sync, 
     update, or scrub user profile metadata from MongoDB.
  2. `send-new-connection-request-reminder` & `send-new-message-email`: Triggers asynchronous SMTP nodemailer delivery 
     so that the API returns a response to the user instantly, without waiting for the slow email server transaction to finish.
  3. `delete-story`: Deletes a story document after a 24-hour delay using `step.sleep('wait-for-24-hours', '24h')`.

Q14: Explain the Story Expiration mechanism. How does it guarantee deletion after 24 hours?
A:
- When a story is created, the story router handles DB entry.
- In the background, the server fires an Inngest event: `inngest.send({ name: 'app/story.delete', data: { storyId } })`.
- Inngest registers the job and suspends execution for 24 hours (`step.sleep('24h')`).
- After exactly 24 hours, Inngest triggers the callback function `delete-story-from-db` which executes 
  `Story.findByIdAndDelete(storyId)`.
- Benefit: It does not require cron jobs running every minute querying the database (which creates load spikes). The cleanup is 
  completely isolated and self-contained per story.

PART 6: FRONTEND & CLIENT-SIDE OPTIMIZATIONS
--------------------------------------------------------------------------------

Q15: How is code splitting set up in the React client, and what problem does it solve?
A:
- Implemented using React `lazy()` and `Suspense`:
  ```javascript
  const Messages = lazy(() => import("./pages/Messages.jsx"));
  ```
- Problem: In a standard SPA, the build pack compiles all pages into a single large JavaScript bundle. On initial load, 
  the browser has to download, parse, and execute the entire bundle even if the user is just looking at the Login page. This 
  slows down the Page Load speed.
- Solution: Lazy loading splits the code into smaller chunks. The browser only downloads the chunk for the current page, 
  loading other pages on-demand when the user navigates to them.

Q16: Explain "Late Querying" and "Memoization Cache" in search inputs.
A:
- Late Querying (Search Thresholds): In the Discover search page, we only trigger search queries when the user types 
  **3 or more characters**. Typing 1 or 2 characters yields too many generic search results and causes unnecessary API roundtrips.
- Memoization Cache: Inside the Discover page, a React `useRef` acts as a cache store:
  ```javascript
  const searchCache = useRef({});
  ```
  Before sending an API request, the code checks if the search keyword exists in `searchCache.current`. If it exists, the app 
  reads directly from the cache. This prevents duplicate API hits when a user deletes/types back and forth.

Q17: Why did we choose TanStack Query (React Query) for feed retrieval?
A:
- It handles complex server state synchronizations out-of-the-box.
- Key features:
  - Cache Management: Caches fetched posts and keeps them fresh using automatic stale-while-revalidate policies.
  - Cursor-based Infinite Scrolling: Integrates with `useInfiniteQuery` to retrieve page segments dynamically 
    (fetching next page using cursor offsets).
  - Outbox Management: Automatically handles request retries on network failures.

Q21: How is Optimistic UI implemented in the chat interface (ChatBox.jsx)?
A:
- When a user clicks send, the application does not block the UI waiting for the server's network response.
- Flow:
  1. Instant Render: A temporary message object is created in memory with a temporary ID (`temp-${Date.now()}`), 
     the input text, and a flag `isOptimistic: true`. This is appended to the `messages` array state immediately.
  2. State Clear: The input text field and image preview states are cleared instantly, giving the user feedback of a successful action.
  3. API Request: The client sends a multipart `FormData` request to `/api/message/send` using Axios.
  4. Success Reconciliation: Once the server responds with the saved database record, the client updates the state by mapping 
     over the message array, finding the message matching the temporary ID, and replacing it with the actual database payload 
     (e.g., getting the real database `_id` and timestamp).
  5. Rollback on Failure: If the request fails, the application deletes the optimistic message from the array, 
     triggers a toast error, and restores the original text and image into the input field so the user doesn't lose their message.

Q22: How is user presence (isOnline) tracked in the ChatBox, and how is it optimized?
A:
- User presence is tracked via Redis keys `presence:${userId}` on the backend.
- On the client (`ChatBox.jsx`), we use TanStack Query with a `refetchInterval` configuration:
  ```javascript
  const { data: userData } = useQuery({
      queryKey: ['user-profile', userid],
      queryFn: async () => { ... },
      refetchInterval: 30000, // Query every 30s to update presence status
      enabled: !!userid
  });
  ```
- Optimization: Rather than calling a specialized, heavy endpoint or using continuous WebSocket heartbeats, the client 
  periodically refetches the user profile document (which is cached on the Redis server for 15 minutes anyway) at an acceptable 
  interval (30 seconds). The controller injects a quick boolean presence check `isOnline = !!(await redisClient.get('presence:ID'))` 
  which runs in $O(1)$ time, keeping the database overhead minimal.

PART 7: BOTTLENECKS, SCALING, & FUTURE IMPROVEMENTS
--------------------------------------------------------------------------------

Q18: What are the main bottlenecks of the current free tier stack?
A:
1. Redis Command Cap: The Upstash Free Tier caps commands at 10,000/day. Because rate limiting and user presence require 
   commands on almost every action, ~50 to 100 highly active users will hit this cap in a single day.
2. MongoDB Atlas Connection Limit: The Atlas M0 free tier caps concurrent connections at 100. If we scale out to multiple 
   app instances, each server pooling 10 connections will exceed this cap.
3. SSE Keep-Alive Memory: SSE requires keeping open TCP/HTTP connections for every online user. A free-tier host (like Render 
   with 512MB RAM) will exhaust its memory limits or file descriptor caps with more than 150-200 concurrent connections.

Q19: How would you scale this architecture to support 100,000+ active users?
A:
1. Database Scaling:
   - Upgrade MongoDB to a dedicated tier (M10+) to lift the connection limits and configure horizontal read replicas.
   - Set up appropriate Sharding on the `messages` collection if the message count balloons.
2. Caching & Scaling Broker:
   - Transition Redis to a dedicated VM instance or clusters to remove command limits and handle tens of thousands of ops/sec.
3. API Servers (Load Balancing & Clustering):
   - Wrap the Node.js server in PM2 Cluster Mode to utilize all available CPU cores.
   - Run multiple server containers on AWS ECS or Kubernetes behind an Application Load Balancer (ALB).
4. SSE scaling:
   - Use a reverse proxy (like Nginx) or a dedicated API gateway (e.g. AWS API Gateway, Centrifugo, or PubNub) to manage 
     persistent SSE/WebSocket connections, keeping the Node.js event loop free from maintaining thousands of idle TCP sockets.
5. Media Delivery:
   - Put a Cloudflare CDN in front of the ImageKit assets to cache image assets globally, reducing transit bandwidth costs 
     and latency.

Q20: How are connection requests protected from spam?
A:
- In `user.controller.js`, connection requests have a built-in application-level throttle:
  ```javascript
  const last24hrs = new Date(Date.now() - 24 * 60 * 60 * 1000);
  const connectionRequests = await Connection.find({ from_user_id: userId, createdAt: { $gt: last24hrs } });
  if (connectionRequests.length >= 20) {
      return res.status(400).json({ success: false, message: "You have sent more than 20 connection requests..." });
  }
  ```
- This prevents automated script abuse (bot accounts spamming everyone on the network) and improves user experience.
